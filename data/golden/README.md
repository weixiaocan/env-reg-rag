# Golden 测试集标注规范

> 这是 P3 阶段的核心产出，也是你（业务专家角色）的主要交付物。
> 对应角色：**业务专家**，不是开发者——标注时不需要看代码。

---

## 你要做的事

从真实工作场景里挑 30 个问题，翻 PDF 找到答案所在的**标准号**和**条款号**，填进
`golden_set.jsonl`。

**就这些。** chunk_id、向量、检索这些都不用管，我建完索引后自动映射。

---

## 为什么是你来标

1. 只有你知道真实工作里会问什么——编出来的问题分布和实际不符，指标会虚高；
2. 标注过程本身会暴露设计盲点（"原来这个问题不该答"、"这份标准我之前没注意"）；
3. 这是项目里唯一不需要写代码但**决定项目成败**的工作。

## 字段说明

每行一个 JSON 对象（JSONL 格式，一行一条，不要格式化成多行）。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | `q001` ~ `q030` |
| `query` | ✅ | 问题原文，用**你真实会怎么问**的说法，不要书面化 |
| `type` | ✅ | 见下方类型表 |
| `std_nos` | ✅ | 期望命中的标准号，如 `["GB 50014-2021"]`。拒答类填空数组 `[]` |
| `clause_refs` | ⬜ | 期望命中的条款号，如 `["4.1.3"]`。不确定就留空 |
| `region` | ⬜ | 涉及地域时填，如 `"北京"`、`"福建"`。无则省略 |
| `as_of_date` | ⬜ | 查历史版本时填适用时点，如 `"2020-06-01"`。无则省略 |
| `should_refuse` | ✅ | 这个问题**应该拒答吗**，`true` / `false` |
| `notes` | ⬜ | 备注，比如"这个容易和 XX 混淆" |

### type 取值

| 值 | 含义 | 例子 |
| --- | --- | --- |
| `clause` | 条款定位 | "GB 50014 里第 4.1.3 条怎么规定的" |
| `concept` | 概念解释 | "什么是雨污混接" |
| `numeric` | 数值查询 | "暴雨重现期一般取多少年" |
| `regional` | 地域适用 | "北京排水管网设计重现期取多少" |
| `cross_doc` | 跨文档对比 | "国标和福建地标对混接改造的要求差异" |
| `should_refuse` | 应拒答 | "我们小区明天会不会积水"（超出知识范围） |

| 类型 | 条数 | 说明 |
| --- | --- | --- |
| `clause` 条款定位 | 8 | 验证切分与精确匹配 |

## 三条硬性要求

### 1. 问题必须来自真实场景，不要编

优先顺序：
1. 你以前被同事/甲方问过的问题
2. 培训或考试里的题目
3. 你写报告时真的翻过标准才答上来的问题
4. 新人工程师最常问的问题

**反面例子**：为了凑数现编一个"请说明排水体制的分类"——真实用户不会这么问。

### 2. 标准号和条款号必须翻 PDF 确认过

不要凭印象填。打开 `data/raw/标准和规范&参考资料/` 下的 PDF，
找到答案实际所在的条款，抄下编号。

**条款号怎么填**：直接抄 PDF 里的写法就行，格式不统一没关系
（"第 3.2.1 条" / "3.2.1" / "3.2.1-1" 都可以），**我会做规范化**。

### 3. 一定要有"应该拒答"的问题

至少 3 条。这类问题的标准是：**知识库里确实没有答案，系统应该承认不知道**。

例子：
- "某某市 2026 年新建管网项目的预算是多少"（不在标准里）
- "这个监测点昨天流量异常是什么原因"（需要监测数据，不在知识库）
- "排水许可证怎么办"（可能是地方行政流程，标准里未必有）

**为什么必须有**：拒答能力是法规类系统的安全底线。
如果 golden 集里没有这类问题，系统"什么都敢答"的倾向不会被发现。

## 常见问题

**Q：一个问题可以有多个正确答案吗？**
可以，`std_nos` 和 `clause_refs` 都是数组，全填上。

**Q：我不确定某个条款在不在知识库里怎么办？**
翻一遍 `data/raw/` 确认。如果确实没有，就把这条改成 `should_refuse`，
或者在 `notes` 里标注"疑似超出范围"。

**Q：标注时发现问题不好分类怎么办？**
按你判断最接近的填，`notes` 里说明即可。分类是为了分析，不是为了难为你。

**Q：30 条标完就够了吗？**
不够。这是**种子集**，POC 阶段会补充到 80 条。
但 30 条已经足够跑第一轮基线和暴露问题——**不要追求一次做完美**。

## 交付方式

填完 `golden_set.jsonl` 后，我会跑一个校验脚本：

1. 检查所有 `std_nos` 是否能在语料库里找到对应文档；
2. 检查所有 `clause_refs` 是否能匹配到实际 chunk；
3. 输出匹配率报告——**匹配率低的条目要回来复核**。

这个校验会告诉你两件事：标错了的条目，以及**语料覆盖不到的场景**（后者更有价值）。
