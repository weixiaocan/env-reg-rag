# 通用 AI 协作开发流程

状态：v0.1，项目内试运行

## 目标

沉淀一套可用于不同 AI 应用和软件项目的协作开发方法。本项目以环保法律法规 RAG 作为第一个真实验证场景，但通用 Skill 不包含 RAG 专属技术要求。

## 四阶段流程

1. `define-spec`：明确问题、用户、范围、需求和验收标准。
2. `design-solution`：设计技术方案，并拆分中等粒度、可验收的开发任务。
3. `build-review`：按规格实现一个任务，运行局部测试并完成独立 Review。
4. `verify-release`：执行完整测试与项目专项评估，基于证据判断是否可以发布。

不设置总控 Skill。流程顺序和阶段状态由本文件及项目文档表达。

## 建设方式

采用“创建一个、使用一个、修订一个”的方式：

1. 创建当前阶段 Skill 的最小可用版本。
2. 立即在真实项目中使用。
3. 记录过程中的摩擦、遗漏和无效规则。
4. 只根据重复出现或影响明显的问题修订通用 Skill。
5. 当前阶段产物通过门控后，再创建下一个 Skill。

项目内版本验证稳定后，再安装为全局个人 Skill。

## 通用规则与项目规则的边界

通用 Skill 规定工作方法、输入输出和质量门控。具体项目文档规定领域内容、技术指标与实施约束。

例如，`verify-release` 要求结论必须有实际测试证据；RAG 项目的 Recall@K、引用正确率和拒答率则写入本项目的测试评估计划，而不是写进通用 Skill。

## 文档约定

- 活跃项目文档统一放在一个文档根目录；没有既有约定时使用 `docs/`。
- 仓库根目录只保留 `README.md` 等工具生态要求的入口文件，不散落 PRD、架构、面试稿或阶段说明。
- 同一目的只保留一个活跃文档；新版本更新原文档，确需保留历史时明确标为 superseded 或移入归档区。
- 默认不在项目产物中写个人真实姓名；审批、维护和评审使用角色名称，除非项目明确要求实名。
- 创建新文档前先检查已有文件和引用关系，避免让后续 AI 同时读取互相冲突的规格。

## 任务粒度

任务以一个可演示、可验证的能力增量为单位，可以跨越多个文件和模块。只有存在真实依赖、风险隔离或上下文容量问题时才继续拆分；不按文件、类或代码层机械创建 ticket。

## 反馈记录

每次流程反馈至少区分：

- 这是通用流程问题，还是当前项目特有问题；
- 它是否真实影响了质量、效率或理解；
- 应修改 Skill、模板、项目文档，还是无需固化；
- 修改后准备如何在后续阶段验证。
