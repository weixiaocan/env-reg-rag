## 2. 黄金测试集（Golden Set）

### 2.1 单条字段（最少三件套 + 元数据）

```json
{
  "id": "G001",
  "question": "用户会问的问题",
  "evidence": [
    {
      "doc_id": "文档标识/标准号",
      "chunk_or_element_id": "可定位到原文的 id",
      "page": 12,
      "quote": "应检索到的原文摘录（证据）"
    }
  ],
  "expected_facts": [
    "答案必须包含的关键事实 1",
    "关键事实 2"
  ],
  "labels": {
    "repr": ["定义"],
    "challenge": ["同义表达"],
    "modality": ["正文"]
  },
  "notes": "可选：易混标准、拒答预期等"
}
```

- **证据** → 评检索  
- **预期事实** → 评生成  
- 多证据题：`evidence` 可多条；Recall 按「必须命中的证据集合」算

### 2.2 50 条怎么铺（代表性 × 挑战性）

**代表性（问题类型，约占比）**

| 类型 | 条数（建议） | 例子方向 |
| --- | --- | --- |
| 定义 / 术语 | 8 | 「什么是…」「…指的是」 |
| 数值 / 限值 | 10 | 流量、坡度、管径、间距 |
| 条件 / 适用 | 8 | 「在…情况下应…」 |
| 范围 / 例外 | 6 | 适用范围、不适用情形 |
| 表格查询 | 8 | 查表取参数、行列交叉 |
| 流程 / 要求 | 6 | 「应如何」「必须满足」 |
| 拒答 / 证据不足 | 4 | 库外问题、信息不够应拒答 |

**挑战性（可与上表组合打标签，每条至少 1 个）**

- 同义表达、多条件、多证据、跨页、表格、相似概念干扰、公式相关、需原文定位

**覆盖约束（设计验收用）**

- **全覆盖**：当前发布语料 `corpus-069284e6d60e` 共 **23 份**主文本，50 条黄金集必须 **每份至少 1 条**（不再用「8 份」门槛）。
- 配额大致：23 份保底各 1 条（23）+ 剩余 27 条按页数/题型密度加权（长标、表格多、易混对优先加到 2–4 条）。
- 表格题 ≥ 8；跨页或多证据 ≥ 6；干扰/易混 ≥ 5；拒答 ≥ 4（拒答可挂在「库外/证据不足」，不占用某份保底名额时需在标签里标明）。
- 先 LLM 草稿 → **人工审核改证据与预期事实**（证据必须可回查原文）。
- 文档清单与建议条数见同目录 `golden_coverage_v1.md`。

### 2.3 存放

建议：`rag-eval/datasets/golden_v1.jsonl`（一行一条），版本号进文件名；失败新案例只追加，不改旧 id。

## 3. 三分法评估

### 3.1 检索评估（只检索，不生成）

输入：`question`  
输出：Top-K chunks（建议同时记 K=5 与 K=10）  
对照：`evidence`

| 指标 | 含义 | 计算 |
| --- | --- | --- |
| Precision@5 | 前 5 里真正相关占比 | 程序 |
| Recall@5 / Recall@10 | 必证据是否找全 | 程序 |
| （可选）NDCG@10 | 排序是否把更相关的提前 | 程序；当前无独立重排，**默认不做**；若以后加 cross-encoder 再启用 |

命中判定（第一版规则，可写死）：

1. 优先：`chunk_id` / `element_ids` 与证据标注交集非空  
2. 否则：同一 `doc_id` + 页码接近 + 文本包含证据 `quote` 关键子串（人工抽检校准）

### 3.2 生成评估（给定金证据，绕过检索）

输入：`question` + 人工确认的 `evidence` 原文  
输出：模型回答  
对照：`expected_facts`

| 指标 | 含义 | 方式 |
| --- | --- | --- |
| 答案正确性 | 是否与预期事实一致 | LLM-as-judge（结构化打分 + 理由） |
| 证据一致性 | 回答是否都能在给定证据中找到依据 | 同上 |
| 完整性 | 预期事实是否遗漏 | 同上（可按事实条数覆盖率） |

拒答类测例：预期为拒答/追问时，单独一条 judge 规则（不应硬编答案）。

### 3.3 端到端评估（真实流水线）

输入：仅 `question`  
跑：检索 →（若有）重排/上下文组装 → 生成  
同时记：延迟、大致 Token/成本  

除沿用检索+生成相关指标外，增加：

- E2E 正确性 / 完整性（judge）  
- 延迟 p50/p95  
- 失败归因标签：`retrieval` / `generation` / `both` / `ok`（由规则或人工/半自动从 Trace 推断）

## 3.4 与真实流水线对齐（来自「梳理RAG系统」）

| 环节 | 现状 | 评估含义 |
| --- | --- | --- |
| 切块 | `v2_chunker`：按条结构断点，~480 token，硬帽 512；表/公式/图整段一块 | 证据标注优先落到 `element_ids` / `chunk_id` |
| 检索 | dense + BM25 + **RRF**；**无**独立 cross-encoder 重排 | 第一版可不强调 NDCG；若以后加真正重排再启用 |
| 生成 | LangChain + 智谱（`LLM_PROVIDER=zhipu`，glm 系）；未配置则 answer 降级 REFUSED | 生成/e2e/judge 默认对接智谱；需保证评测环境有可用 key |
| 工作台 | FastAPI + `static/index.html`，`http://127.0.0.1:8000/` | e2e 可走 HTTP API 或同进程调用，避免只测脚本旁路 |
| 已知风险 | 答非所问、漏引/错引、溯源、新入库标准可问性；勿宣传增量入库/全量质量门禁已上线 | 黄金集应覆盖「易混标准、应拒答、需溯源」题型 |

## 4. Evaluation Harness + Trace

第一版保持轻量（与文章一致）：**脚本 + 结果 JSON + 简单 HTML**。

### 4.1 Harness 职责

1. 读 `golden_v1.jsonl`  
2. 按模式跑：`retrieval` | `generation` | `e2e`  
3. 落盘每条 run 结果  
4. 调程序指标 + LLM judge  
5. 汇总一轮 summary（均值、分类型分层、对比上一轮）

建议目录：

```text
rag-eval/
  datasets/golden_v1.jsonl
  runs/<run_id>/
    config.json          # 模型、K、prompt、语料版本
    cases/<id>.json      # 单条完整 Trace
    summary.json
    report.html
```

### 4.2 单条 Trace 必须看见的字段

- 问题、预期事实、证据  
- 实际检索 Top-K（id、分数、摘录、页码）  
- 送给模型的最终上下文  
- 生成答案  
- 各项指标分数 + judge 理由  
- 耗时拆分（检索 / 生成）

> Harness 负责自动跑；Trace 负责失败时能顺着链路查到哪一步错了。

### 4.3 与现有代码的衔接

- 检索：复用 V2 混合检索 + Qdrant `corpus_v2`（dense + BM25 + RRF）  
- 生成：对接现有工作台/服务（智谱 GLM）；Harness 抽象 `retrieve` / `generate(question, contexts)` / `answer_e2e(question)`  
- 权威文档在用户机仓库：`docs/SCOPE_AND_DEFERRED.md`、`docs/v2-canonical-schema-design.md`；box 上 `rag-prechunk` 仅作参考副本，以本机 `env-reg-rag` 为准  
- 现有诊断回归 / `EVALUATION.md` **不替代** 本黄金集问答评估

## 5. 迭代方式

1. 跑出 **Baseline**（golden_v1 + 当前语料/检索/prompt）  
2. 每次只改一个主变量（切块 / 检索参数 / prompt / 重排）再同集复跑  
3. 新失败案例补进黄金集 → 回归
